# 無料で2時間ごとに板を保存・リセットする導入セット

GitHub Actionsで毎日、日本時間の奇数時17分（01:17、03:17…23:17）に期限を確認します。設定された14日を過ぎた最初の実行で画像保存→次の板へ切り替えます。開始時刻は新しい板を作成した時刻です。「毎月1日・15日」という日付指定ではありません。

Firebaseを無料のSparkから変更する必要はありません。公開リポジトリの標準GitHubランナーは無料です。Firebase/Supabase自体の保存容量・通信量は既存の無料枠を消費します。GitHubの混雑による遅延・実行の欠落があるため、時刻の厳密な保証はできません。次の実行でも期限切れを判定します。公開リポジトリは60日間活動がないと定期実行が無効になるため、Actionsの状態を確認してください。停止された場合はGitHubで定期実行を再有効化します。

## 同梱物を配置する

ZIPを解凍し、公開サイトを置いているGitHubリポジトリのルートに、次のように配置してください。

```
.github/workflows/board-reset.yml
server-reset/database.rules.json
server-reset/functions/package.json
server-reset/functions/package-lock.json
server-reset/functions/core.js
server-reset/functions/render.js
server-reset/functions/run.js
server-reset/functions/test/*.test.js
index.html
```

`index.html` は本筆改善・二重リセット修正・サーバー担当モードへの対応を含みます。先に現行HTMLをバックアップしてください。既存のmanifest、sw.js、アイコンは同じ場所で使います。PWAに旧版が残る場合はキャッシュの更新が必要です。古いHTMLが開いていても、新しいFirebaseルールで板送りを拒否します。

## GitHubに2つのSecretsを登録する

GitHubリポジトリの Settings → Secrets and variables → Actions → New repository secret に登録します。鍵をリポジトリのファイルやindex.htmlに書かず、チャットにも貼らないでください。

1. `FIREBASE_SERVICE_ACCOUNT_JSON`
   Firebaseコンソール → プロジェクト設定 → サービスアカウント → Firebase Admin SDK →「新しい秘密鍵の生成」で取得したJSONの全文です。対象プロジェクトは `fg21-dk2027-writeboard` です。
2. `SUPABASE_STORAGE_SERVER_KEY`
   Supabaseの `oicwpmyvophbzfaqfbka` プロジェクトで取得したサーバー用secret keyまたはservice_roleキーです。現在のHTMLにあるanonキーではありません。board-imagesバケットの画像を読む・保存する・失敗した保存を削除するために使います。

Firebaseの秘密鍵作成が組織ポリシーで禁止されている場合は、この方法を使わずWorkload Identity Federationで認証する構成への変更が必要です。

## 変更の順序

1. 既存のFirebaseルールとHTMLをバックアップします。
2. GitHubに上記ファイルとSecretsを登録します。初期状態ではサーバー担当モードが未設定なので、定期処理は板を変更しません。
3. Firebase → Realtime Database → ルールで、`server-reset/database.rules.json` の全文を貼り付けて公開します。提供いただいた既存ルールの権限を基に、サーバー担当モードと古い板への書き込み防止を追加しています。
4. GitHubのActions →「Board archive and reset」→ Run workflow を開き、`dry_run` をチェックしたまま実行します。ログに板番号・日数設定・開始時刻・期限切れ判定が表示されます。この確認では保存も切り替えもしません。
5. 2つのSecrets、画像を置く既存バケット、公開HTMLの動作を確認したら、Firebase → Realtime Database → データの `/meta` に `serverReset` を追加します。型は **boolean**、値は **true** です。文字列の `"true"` は使いません。`resetDays` は number の `14` にしてください。
6. Run workflow で `dry_run` のチェックを外して一度実行します。板が期限切れなら保存して切り替えます。期限前なら何も切り替えません。
7. 次の定期実行が成功していることと、運営の履歴画面に画像が出ることを確認します。

Secretsの登録や本番への変更は、この導入セットの作成時点ではまだ行っていません。

## 動作と制限

- 全画像を読み込み、6000×2200のクリーン画像を合成します。縦横の比率、回転、お題枠のグリッド位置を反映します。1枚でも画像が欠けると切り替えを中止します。
- 保存した画像を再読込してサイズを確認した後、履歴記録・次の板の開始日時・現在の板番号を一つのトランザクションで変更します。
- 保存中に投稿や位置・枠が変わると切り替えません。未確定画像を削除し、次の2時間後の実行で再試行します。
- 古い板・投稿データはFirebaseに残します。画像化済みの古い板への書き込みは止めます。
- 日数のほか、既存の枚数上限に達した板も次の定期実行で切り替えます。枚数上限に達すると、その実行までは新しい投稿が入らない場合があります。
- 空の板も14日を過ぎると1回切り替えます。停止期間を取り戻すために空の板を連続作成することはしません。
- サーバー版は **クリーン画像** を保存します。背景・ロゴ・UIを含む「見たまま」画像は履歴の「見たまま再出力」で必要時に作成してください。
- サーバー担当モード中、ブラウザーの「保存して新ボード」は停止します。履歴からの画像再出力は利用できます。導入前のpendingArchiveは自動処理しません。古い未保存板は履歴の板番号指定から再出力できます。
- 元の次の板番号にデータが既に存在する場合は上書きせず停止します。データ確認後に板番号の進め方を調整してください。
- Firebaseのトランザクションはルートで行うため、切り替え時に過去の板を含むデータを読みます。日数確認だけの実行では現在の板を読みます。大量の過去データがある場合、無料枠の通信量に注意して運用してください。

## 失敗時・戻す時

失敗はGitHub Actionsの赤い実行結果とログで確認します。GitHubのActions通知を有効にしてください。次回も期限切れを拾います。ルールとモードが整っていれば、失敗しても現在の板を消したり番号だけ進めたりしません。

従来のブラウザー担当に戻す場合は、まずGitHub Actionsのこのworkflowを無効化し、`/meta/serverReset` を boolean の false にします。ブラウザー方式には「運営が開いていないと画像保存できない」制約が戻ります。

## 確認済みの範囲

ローカルで期限・二重実行・投稿競合・保存失敗・画像欠落・クリーン画像合成・ルール式の単体テストとHTML構文チェックを実施しています。Firebaseエミュレーターでのルール検証と、GitHub上の本番実行は未実施です。公開前に上記のdry_runと最初の実行で確認してください。
